Page Object 设计模式

为什么需要 POM？

在没有 POM 的项目中，测试代码通常"散落"着 page.locator("#username").fill("admin") 这样直接的元素操作。当 UI 改版（例如 #username 变成 [data-testid=username]），需要修改几十个测试文件。POM 将元素定位集中管理，修改一处即可。

基础 POM 示例

pages/login_page.py
class LoginPage:
    '''Elements centralized - change once, fix everywhere'''

    def __init__(self, page):
        self.p = page
        self.url = "/login"
        self.username = page.get_by_label("Username")
        self.password = page.get_by_label("Password")
        self.submit = page.get_by_role("button", name="Login")

    def goto(self):
        self.p.goto(self.url)
        return self

    def login(self, user, pwd):
        self.username.fill(user)
        self.password.fill(pwd)
        self.submit.click()
        return DashboardPage(self.p)


class DashboardPage:
    def __init__(self, page):
        self.p = page

    def assert_loaded(self):
        expect(self.p).to_have_url("/dashboard")
        return self


# Test becomes extremely clean
def test_login(page):
    LoginPage(page).goto().login("admin", "Test@123").assert_loaded()

带组件化的 POM

复用组件示例
# 组件：可复用的表格操作
class DataTable:
    def __init__(self, container):
        self.c = container

    def rows(self):
        return self.c.locator("tbody tr").all()

    def get_row_by_text(self, text):
        return self.c.locator("tbody tr", has_text=text)

    def sort_by_column(self, name):
        self.c.locator("th", has_text=name).click()

    def assert_row_count(self, n):
        expect(self.c.locator("tbody tr")).to_have_count(n)


# 页面：使用 DataTable 组件
class UserListPage:
    def __init__(self, page):
        self.p = page
        self.table = DataTable(page.locator(".user-table"))

    def goto(self):
        self.p.goto("/admin/users")
        self.table.assert_row_count(10)
        return self
💡 POM 设计原则
  • 方法返回 Page Object：每个动作方法返回它导航到的下一个页面对象（如 login() 返回 DashboardPage），让测试代码形成流式调用链。
  • 不暴露 locator：所有 locator 设为 private/前缀下划线。测试代码只调用业务方法，不直接操作 page.locator()。
  • 组件化复用：DataTable、Modal、DatePicker 等跨页面复用组件独立封装，页面通过组合引用。
  • 断言内聚：将 expect() 调用放在 Page Object 的 assert_* 方法中，而非散落在测试函数里。
⚠️ 避坑指南：元素定位的脆弱性
  • 避免 CSS class 定位：前端框架生成的 class 名（如 css-1abc2de）在每次构建时可能变化。优先使用 getByRole()、getByLabel()、getByTestId()。
  • XPath 性能陷阱：复杂的绝对 XPath 在大 DOM 树中定位极慢。Playwright 的 text= 和 has-text= 比 XPath 快 10-100 倍。
  • 隐式等待 vs 自动等待：不要使用 time.sleep()。Playwright 的自动等待机制（actionability checks）已覆盖绝大多数场景。
  • 页面对象膨胀：一个 Page Object 超过 200 行时，意味着它承载了太多职责。按功能区域或组件拆分。
