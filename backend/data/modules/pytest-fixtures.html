Fixtures 深度用法

test_fixture_patterns.py
import pytest


# 1. yield fixture — setup/teardown
@pytest.fixture
def db():
    conn = create_connection()
    yield conn      # test runs here
    conn.close()    # teardown


# 2. Fixture chaining
@pytest.fixture
def user(db):       # auto-depends on db
    u = db.insert_user("test")
    yield u
    db.delete_user(u.id)


# 3. Factory pattern — parameterizable creation
@pytest.fixture
def make_user(api):
    created = []
    def _create(name="test", role="user", **kw):
        u = api.create(name=name, role=role, **kw)
        created.append(u)
        return u
    yield _create
    for u in created: api.delete(u["id"])

def test_roles(make_user):
    admin = make_user(role="admin")
    viewer = make_user(role="viewer")

Fixture 生命周期与作用域

理解 pytest fixture 的生命周期对于避免测试间数据污染和优化执行效率至关重要。下图展示了一个完整测试会话中不同 scope 的 fixture 何时被创建和销毁。

sequenceDiagram
    participant Session as pytest Session
    participant Module as conftest.py
    participant Class as Test Class
    participant Test as Test Function

    Note over Session: scope="session"
    Session->>Module: setup (once)
    Module-->>Session: session fixture ready

    Note over Module: scope="module"
    Module->>Class: setup (per module)
    Class-->>Module: module fixture ready

    Note over Class: scope="class"
    Class->>Test: setup (per class)
    Test-->>Class: class fixture ready

    Note over Test: scope="function" (default)
    Test->>Test: setup before each test
    Test->>Test: test body runs
    Test->>Test: yield pause
    Test->>Test: teardown after test

    Test-->>Class: function fixture cleaned
    Class-->>Module: class fixture cleaned
    Module-->>Session: module fixture cleaned
    Session-->>Session: session fixture cleaned

Scope 参数决策树

function（默认）

每次测试函数都重建 fixture。适用于有状态/可变数据。

用例：临时数据库记录、浏览器 page

class

同一 TestCase 类内所有方法共享。少用，因为 pytest 更鼓励函数式风格。

module

同一个 .py 文件内所有测试共享一次 setup。

用例：加载 JSON 配置文件、数据库迁移

session

整个测试运行期间只执行一次 setup/teardown。

用例：启动本地服务器、全局 HTTP Client

💡 Fixture 工厂模式 vs 参数化 — 选择指南
  • 工厂模式（factory as fixture）：当测试内部需要动态创建多个不同对象时使用。例如一个测试需要同时创建 admin 和 viewer 两种用户。
  • pytest.mark.parametrize：当你希望对同一个测试逻辑用多组数据进行独立运行时使用。每组数据是一次独立的测试执行，失败不会互相影响。
  • pytest_generate_tests：当参数化数据需要根据命令行参数、配置文件或外部服务动态生成时使用。比 parametrize 更灵活但更难调试。
  • 判断标准：如果你在想"这个 fixture 应该是什么 scope"，先画数据依赖图再看 scope。
⚠️ 避坑指南：Fixture Scope 混用的隐性 Bug
  • session 依赖 function：如果一个 session-scoped fixture 依赖了一个 function-scoped fixture，pytest 会报错。这是因为 session 只创建一次但 function 每个测试都要重建，逻辑矛盾。
  • module 间数据泄漏：若 session-fixture 修改了共享状态（如全局配置 dict），所有后续 module 都会受影响，排查极其困难。解决方案：fixture 返回只读对象或 deep copy。
  • yield 后的异常：teardown 代码（yield 之后）中的异常会被 pytest 捕获并报告，但不会阻止其他 teardown 继续执行。teardown 失败可能导致资源泄漏（文件句柄、数据库连接未关闭）。
  • conftest 覆盖规则：子目录的 conftest.py 会覆盖父目录的同名 fixture，但仅在当前作用域。如果 fixture 链跨越多个目录层级，覆盖顺序可能出乎意料。
